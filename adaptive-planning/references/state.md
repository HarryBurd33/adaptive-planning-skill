# Planning state and optional integrity helper

Store one JSON file per planning process **outside the installed skill**, for example a user-chosen private `planning/state.json`. The bundled [template](../templates/state.json) contains synthetic dates and a synthetic sleep window: replace them from user information; never treat them as the user's preferences. Schema: [state.schema.json](../state.schema.json). Basic planning does not require Python, filesystem access, Compass, Obsidian or a calendar.

## Contract, version 1

Every listed field is required. Empty arrays mean no recorded items, not proof that none exist. `null` means unknown/not applicable, never zero. Objects reject unrecognized fields except the top-level `extensions` object, which holds additional profile/preferences, capacity calculations, milestone views, assumptions, coverage notes and host metadata. Preserve extensions by default. For intentional planning recalculations, select only the named keys to replace or add with repeatable `--replace-extension KEY`; preserve all other keys verbatim. This operator selection uses the already authorized planning scope and does not require another user confirmation. A selected key must remain present in the proposal; deletion is not supported.

- Root: `schema_version: 1`, stable `plan_id`, nonnegative integer `revision`, aware `updated_at`, `profile`, `tasks`, `occurrences`, `fixed_events`, `model_week`, `dated_plan`, `progress`, `feedback`, `adaptations`, `applied_updates`, `extensions`.
- `profile`: IANA `timezone`; `week_start` 0=Monday through 6=Sunday; `sleep` either unknown `null` or `{start,end}` local `HH:MM`. An end earlier than the start is the next morning. Equal endpoints are invalid. Additional sleep exceptions/protected time can be represented explicitly as dated protected events; this helper supports one normal daily sleep window, not an exception solver.
- Each task: stable `id`, `title`, nullable nonnegative integer `remaining_minutes`, nullable aware `deadline`, nullable `preferred_date` (`YYYY-MM-DD`), `priority` (`high/medium/low`), `required` and `flexible` booleans, `dependencies` (task IDs), positive integer `min_session_minutes`, nullable `recurrence`. Do not invent values merely to complete a schema: leave unknown effort/deadline null, record assumptions/unknowns in extensions, ask only consequential questions. A provisional priority or flexibility classification must be disclosed as such.
- Recurrence: `{frequency: daily|weekly|monthly, count: positive integer, minutes: positive integer}` means count sessions **per full local period**. A daily period is midnight to next midnight; a week begins on `week_start`; a month begins on day 1. These periods have exclusive end dates. Do not reset a week at a month boundary. For a requirement not well represented by these units, keep an explicit task/occurrence inventory and explain the modeling limit rather than silently changing it.
- Each occurrence: `id`, `task_id`, `period_start`, exclusive `period_end`, `remaining_minutes`. ID format: `TASK@FREQUENCY:PERIOD-START#N`, where N is 1..count. Example: `lift@weekly:2026-10-26#1`, period `[2026-10-26,2026-11-02)`, remains the same occurrence in October and November views. Partially completed occurrences retain their IDs and reduced remaining effort; no automatic habit debt carries into a new period. Materialize full periods touching the current dated horizon; preserve earlier progress in history.
- Fixed/protected events: `{id,title,kind,start,end}`. `kind` is `fixed`, `protected`, `transition`, `meal`, `break`, `buffer` or `unavailable`. Enter dates with local wall time and explicit correct UTC offset in the profile zone. Sleep is checked separately. Reserve buffer explicitly or record its calculation in extensions; the helper does not invent buffers/availability.
- `model_week`: separate normal-routine entries `{weekday,start,end,task_id,label}`; weekday is 0=Monday through 6=Sunday; task_id is null or an existing task ID. Equal start/end is invalid. An end earlier than the start denotes the following day, including Sunday into Monday. These are local recurring wall times, not dated DST assignments. A dated exam/meeting exception changes the dated plan, not this array. Only a deliberate durable, reversible adaptation changes model_week.
- `dated_plan`: local `start` date, exclusive `end` date, canonical `blocks`, `unscheduled`. Each block is `{id,task_id,occurrence_id,start,end,status}`; occurrence_id is null for nonrecurring tasks and a matching ID for recurring work; status is `planned` or `completed`. Nonrecurring tasks reference their task ID. Each unscheduled entry is `{task_id,occurrence_id,minutes,reason}`; nullable minutes expresses unknown effort. Maintain one block inventory; daily/weekly/monthly displays derive from it, without duplicating work.
- Progress: `{id,task_id,occurrence_id,observed_at,remaining_minutes,actual_minutes,note}`; actual_minutes may be null. Remaining effort is an absolute observed/estimated value, not an instruction to decrement twice. Mark completed blocks and reduce corresponding remaining effort once. Preserve completed work, elapsed time and unaffected future blocks during replanning.
- Feedback: `{id,observed_at,text}`. Record explicit user instructions here too so adaptations can cite them. Missing reports remain unknown.
- Adaptations: `{id,observed_at,evidence_ids,before,after,reason,reversible,reverts}`. `before`/`after` are objects, evidence_ids reference recorded feedback/progress, reversible is normally true, reverts is null or the ID of the decision being reversed. Apply justified reversible changes with an explanation. Append a reversal record instead of rewriting historical evidence. The helper verifies evidence IDs exist, but cannot establish whether the evidence justifies the decision.
- Applied updates: `{id,sha256}` records maintained by the commit helper, not a user-facing activity log. Preserve it. Stable update IDs identify the same logical update across retries.

## CLI

Requires Python 3.9+ and an installed IANA timezone database (`zoneinfo`). Some platforms need timezone data provisioned separately. No network or third-party packages are used. When the runtime/timezone database is absent, perform the checks conversationally and disclose the unavailable deterministic verification.

```sh
python3 /path/to/adaptive-planning/scripts/planning_state.py check /private/planning/state.json
python3 /path/to/adaptive-planning/scripts/planning_state.py commit /private/planning/state.json /private/planning/proposed.json --expected-revision 4 --update-id update-2026-11-04-meeting --replace-extension capacity
```

Read current state first. Copy and edit a proposal at the **current** revision. The helper checks it, increments revision once, stamps UTC updated_at, appends update ID/content hash and atomically replaces current state. Retry with the same update ID and **the identical original proposal file and the same set of --replace-extension keys**: it returns duplicate success without applying progress again, even if expected revision is now old. Reusing the ID with different content or a different selected-key set fails. The idempotency digest covers both the proposal and the sorted selected-key set; flag order and duplicate flags do not change that set. For a new change, reread current state and use a new update ID. Initial state creation is explicit: copy the template to a new private path, fill known inputs, check it; commit intentionally requires an existing current file and never resets one.

A neighboring `.lock` file serializes cooperating writers. An existing lock blocks the operation and is retained. Never auto-delete it: establish that the recorded process/operation ended and reconcile the current file first. Stale revisions, identity changes, unselected extension changes, deletion of existing task/occurrence IDs, history deletions/edits and edits/deletion of completed blocks are rejected without replacing state. Keep the existing state and conflicting proposal for review. Writes use a same-directory temporary file, fsync and atomic replacement; this is single-file cooperative integrity, not distributed ownership, a database, an encrypted store or a guarantee against arbitrary external editors. Never put credentials in planning state.

## Meaning and limits of checks

`check` emits JSON `{valid,errors,warnings,totals,outside_horizon}`. Exit 0 / valid=true means known syntax and checked constraints pass; it **does not mean the entire plan is feasible**. Always inspect warnings. Exit 2 indicates malformed data or checked constraint errors. `commit` may store honest incomplete state with warnings, but rejects errors. It emits `{committed,duplicate,revision,warnings}` or `{error}`.

The helper checks schema shape and weekday bounds; model-week task references and nonempty sessions; duplicate task/occurrence/block/event IDs; scheduling offsets and nonexistent DST times; positive elapsed block duration using UTC; fixed/task/protected overlaps; ordinary overnight sleep; task minimum sessions; planned deadline violations; dependency cycles and known order; recurrence period/identity/inventory; scheduled versus remaining effort; progress task/occurrence references and adaptation reversal references to prior recorded decisions. Totals count **planned** blocks against **remaining** work; completed blocks are historical and are not counted again. Missing recurrence inventory and unknown/unallocated effort are explicit warnings. A weekly occurrence spanning two months stays one item. Current `totals` includes recurring occurrences only when their full periods touch the dated horizon (`period_start < dated_plan.end` and `dated_plan.start < period_end`). All records are preserved. Out-of-horizon recurrence entries appear separately in `outside_horizon`, keyed by occurrence ID, with `{relation: historical|future, remaining_minutes}`; they do not contribute to current quota/unallocated warnings and are not automatically called missed or carried forward as habit debt. Outstanding nonrecurring tasks remain in current totals regardless of their age.

The helper does not infer whether unscheduled time is available, solve placement, compute the user's usable-capacity budget, prove every dependency fully satisfied, verify natural-language preferences, validate the reasonableness of adaptations, model multiple sleep windows/exceptions, check model-week overlaps, enforce all elapsed-block preservation, or build monthly milestone views. The assistant must perform those checks and report uncovered constraints/shortfalls. Never describe a warning-bearing incomplete plan as fully feasible. Multi-scale coherence follows from the one canonical dated inventory plus the assistant's review; the helper does not compare prose displays.

## Portable handoff

Without durable storage, return the relevant JSON state or a compact text handoff preserving: state version/plan ID/revision and as-of date/timezone; known and unknown profile/constraints; task and occurrence IDs with deadlines, dependencies and remaining work; normal model week; canonical future blocks plus completed/partial progress; unmet requirements; evidence-linked adaptations with before/after/reversal; latest update IDs; assumptions and next action. Omit irrelevant empty fields for conversational brevity, but label the handoff as a compact rendering that must be normalized against the schema before helper use. Never claim cross-chat memory. When resuming, read the handoff/current file, check freshness and conflicting versions, preserve both on disagreement, then continue only the authorized current request.
